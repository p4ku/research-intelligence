Headline. The mechanics are sound for a demo and the German register is right (consistent Sie, typographic „quotes“, deliberate loanwords). What will land badly with Schwarz Digits is (1) the login screen is English-only and a German browser is never detected, (2) the “In Kürze” paragraph on the dashboard and every briefing is English — and it is frontend-generated template prose, not backend content, so the “chrome-only” rule does not excuse it, (3) engineering notes are visible to end users in both languages (“arrive with the backend’s reporting step”, “storage key shown for reference”, a raw cron string), and (4) a handful of German word choices — the false friend Auto-Brief, first-person Lese den Volltext…, 0 gefragt — read as machine-translated. All of the P0 items below are a day's work.

Backend and content language (a decision for the Schwarz Digits conversation)

  • Everything generated is English by default and nothing is configurable: chat system prompt has no language instruction (backend/chat/engine/orchestrator.py:73-80) so a German question gets whatever the model chooses; the briefing narrative (tasks/step_7_reporting/narrative.py) and digest e-mail (templates/emails/pipeline_digest.html, subjects in tasks/auxiliary/email_digest.py:228-230) have no language parameter; the MCP server mandates English output (mcp_server/server/app.py:280).
  • Django: LANGUAGE_CODE='en-us', no LocaleMiddleware (django_project/settings.py:98-108, 214); the BFF forwards only Authorization (src/lib/api/server.ts:35-42). Consequence: DRF/password-validator messages (“This password is too short…”) reach the German settings form in English. Django ships German for all of these — LocaleMiddleware + forwarding Accept-Language: de from the BFF is nearly free.
  • Recommendation: state the policy explicitly in the UI/docs (“Research content is shown in the language of the source; the interface is available in German and English”), add a workspace-level language for narrative + digest, and add “Answer in the language of the question” to the chat prompt. English content + German chrome is defensible for a paper scanner — but it should be a stated choice, not an accident.

3 · Word choice — German dictionary

Register is consistently formal (Sie/Ihr) and typography is right („“, –, …). Loanwords Paper/Papers, Briefing, Screening, Score, TRL are the right call for a Schwarz Digits audience — the issues below are consistency and a few genuine mis-hits.

English copy (native-speaker read for a non-native audience)

  • Idioms that don’t travel: “deep-dived”, “surfaced”, “cleared the signal bar”, “pencil out”, “drill in”, “dig in”. Plain equivalents: “passed the threshold”, “analysed in depth”, “open”.
  • Engineering vocabulary in user copy: backend, endpoint, storage key, contract, persisted, reporting step, extraction definitions, funnel, turns, tokens, grounded. Keep tokens/grounded if the audience is technical; drop the rest.
  • Case inconsistency creating duplicate keys: “Signal score”/“Signal Score”, “Schwarz fit”/“Schwarz Fit”, “Headlines”/“Headline stories”.
  • Spelling mix: PRODUCT.md uses UK (“Rigour”), login uses US (“authorized”). Pick one; en-GB matches the en-GB date choice above.

5 · What is already right

Server/client split is clean: the cookie seeds LanguageProvider once per render, the toggle rewrites the cookie and router.refresh()es so server components follow; shared server+client components take t as a prop with an identity default (scanner-ui.tsx, score-variables.tsx) and every caller passes it. Gettext-style context (nav|Ask) handles homonyms. Identity translations are deliberate loanwords, not omissions. The chrome/content boundary is documented in the dictionary header and in docs/backend-swap-notes.md. Edition dates and Studio timestamps set an explicit time zone. Fonts are self-hosted “for a German corporate deployment”. bun run screenshots --lang de exists and made this evidence cheap to gather.
