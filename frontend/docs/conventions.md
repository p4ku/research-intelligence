# Working conventions

Several people and several agents work in this checkout at once, and the repo
carries the Django backend and shared docs alongside this app. Most of what
follows exists because ignoring it costs somebody else an afternoon.

## Our provenance is `frontend/`

Work from here changes `frontend/` and nothing else. The backend and the
shared `docs/` belong to other people; an incidental edit there lands in
their review queue and conflicts with work we cannot see.

`bun run scope:check` compares the branch against `origin/main` and fails on
any changed file outside `frontend/`. It runs as part of `bun run check`.

This is a default, not a prohibition. A change outside `frontend/` is fine
when it is the point of the branch — give it its own PR and say so in the
description, rather than letting it ride along with unrelated work.

## One command before you commit

```bash
bun run check      # format, types, lint + contract specs, tests, scope
```

Run it from `frontend/`. It is the same set CI would run if CI ran anything
for this app — which it currently does not, so the discipline is ours to
keep. `bun run build` is deliberately not in it: it is slow, and worth
running by hand when you have touched config, routing, or the build itself.

After switching branches, `bun install --frozen-lockfile`. Dependencies land
on `main` regularly and a stale `node_modules` shows up as a confusing
`Cannot find module` from `tsc` rather than as anything about installs.

## Prettier owns formatting

Do not hand-format, and do not argue with it in review. `bun run format`
writes; `bun run check` verifies. Two things are deliberately excluded in
`.prettierignore` and must stay that way:

- **`contract/*.openapi.json`** are generated by `scripts/contract-spec.ts`
  and compared byte-for-byte against its own `JSON.stringify` output.
  Formatting them breaks `bun run lint`.
- **`tsconfig.json`** is rewritten by Next with the current `BUILD_DIR`, so
  every agent holds a different copy of it.

## Feature flags are read at the page layer

The three demo flags (`all_papers`, `stars`, `ask`, registry in
`src/lib/features.ts`) live in one readable cookie and default ON. Read them
in exactly two kinds of place:

- **Server**: a `page.tsx` or a `loading.tsx` calls `getFeatures()` from
  `src/lib/features-server.ts` (or `requireFeature(key)`, which `notFound()`s
  a hidden route). A page and its `loading.tsx` each read once, so a Suspense
  fallback and its content cannot disagree mid-stream.
- **Client**: a `'use client'` component calls `useFeatures()`. It needs no
  prop, and with no provider — a unit render — every flag reads ON, so a
  component in isolation shows its full self.

Never below that. Not in a service, not in a BFF route handler, not in
`src/proxy.ts`: hiding is a UI concern, and the cookie is a preference the
visitor owns, not an authorization boundary.

Server components and skeletons take **one** prop, `features: Features`, not
one boolean per flag. It is **required**, so `tsc` finds the call site you
missed — except on the handful of components `src/app/studio/skeletons/page.tsx`
renders directly, where it is optional with `= ALL_ON`: the gallery must show
every shape whatever the demo cookie says, and `bun run skeleton:drift` must
measure the product rather than a cookie.

## Files that are never committed

- **`tsconfig.json`** — see above. Discard it (`git checkout -- tsconfig.json`)
  rather than staging it; it will be dirty again after the next `next dev`.
- **`local-data/`** — pulled production snapshots. Real data, and large.
- **Build directories.** Give yours a distinct `BUILD_DIR` so parallel builds
  do not fight (`BUILD_DIR=.next-alex bun run dev`); `.gitignore` covers
  `/.next-*/`, whatever you name it.

Stage by name. `git add -A` in a shared checkout picks up whatever anyone
else happened to leave in the tree.

## Real data locally

The production snapshot replay is in the README under _Real data locally_.
Prefer it over mocks when judging a UI change: the fixtures are tidy in ways
production is not, and layouts that only break on real values — long titles,
low scores, missing fields — are the ones worth catching.
